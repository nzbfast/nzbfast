⚡ nzbfast

מוריד ה-Usenet המהיר - מדריך למשתמש

1 · ברוכים הבאים

nzbfast מוריד מ-Usenet מהר ככל שהקו שלך, הספקים שלך והמכונה שלך מתירים - ובדרך כלל זה אומר מהר כמו הקו שלך. זהו תוכנית עצמאית יחידה: המנוע, לוח מחוונים בדפדפן, דפדפן מדיה של קיר פוסטרים, אינדקסר מובנה, תצוגה מקדימה בזמן אמת, תיקון PAR2 מקורי, וחילוץ RAR מקורי - כולם בתוך קובץ הפעלה אחד. אין שום דבר אחר להתקין.

מה שהופך אותו למהיר הוא ארכיטקטורה, לא כיוונונים:

  • NNTP בצנרת - בקשות מאמרים רבות רוכבות על כל חיבור בזו אחר זו, ושומרות כל חיבור במהירות מלאה במקום להמתין להלוך-ושוב.
  • צינור עיבוד במעבר יחיד - הורדה, אימות וחילוץ חופפים. כרכי ארכיון מחולצים בתוך הזרם; בפוסט טיפוסי במצב אחסון קובצי ה-RAR לעולם לא נוגעים בדיסק שלך, כך שהמשימה צריכה פי 1 מגודל הרליס, לא פי 2, ומסתיימת כשההורדה מסתיימת.
  • איחוד מרובה-ספקים - כל שרת מוגדר תורם; מאמר שחסר בעמוד שדרה אחד מורד מאחר. שרתים איטיים או מתים לעולם לא תוקעים את התור.
  • תקציב זיכרון - המנוע מסתגל להקצאת RAM חסומה ו מתדרדר לדיסק אם צריך. הוא לעולם לא מבצע swap במכונה שלך.

נמדד מול השדה על חומרה, משימות וספקים זהים, nzbfast סיים הורדה של 190 GB תוך כ-5 דקות על קו 10 GbE - כאשר החלופות המובילות פיגרו ב-30–220% באותן בדיקות, היכן שהשלימו אותן בכלל. המספרים נמצאים ב-§3.

2 · התחלה מהירה

macOS

  1. פתח את nzbfast-<version>-macos.dmg וגרור את NzbFast אל Applications (אוניברסלי: Apple Silicon + Intel).
  2. הפעלה ראשונה: macOS מזהיר ש-nzbfast עדיין אינו מאושר-נוטריון של Apple. לחץ ימני על האפליקציה → Open - או פתח את System Settings → Privacy & Security, גלול למטה, ולחץ Open Anyway. זהו שלב חד-פעמי.
  3. חלון האפליקציה מציג את לוח המחוונים עם כרטיס ברוכים הבאים - לחץ עליו והוסף לפחות שרת Usenet אחד (מארח, פורט 563, שם משתמש, סיסמה). אפשר להוסיף עוד מאוחר יותר ב-Settings.
  4. הנח קובץ .nzb בכל מקום על לוח המחוונים - או פשוט לחץ פעמיים על קובצי .nzb ב-Finder. הורדות נוחתות ב- ~/Downloads/nzbfast. צא מהתפריט; הורדות מתחדשות היכן שהופסקו.

מעדיף בלי אפליקציה? ה-zip הפשוט (בינארי + משגר Start nzbfast.command, אותו מנוע) עדיין עובד כמו קודם - השלבים למטה תחת "מטרמינל".

Windows

  1. הרץ את nzbfast-<version>-windows-x64-setup.exe. הוא מותקן למשתמש שלך בלבד (בלי סיסמת מנהל). מכיוון שמהדורה זו עדיין אינה חתומה בקוד, SmartScreen עשוי להציג "Windows protected your PC" - לחץ More info → Run anyway.
  2. nzbfast חי במגש המערכת: לחץ פעמיים על סמל המגש (או השתמש ב- Open Dashboard בתפריט הלחיצה הימנית שלו) כדי לפתוח את לוח המחוונים, ואז הוסף את שרת ה-Usenet שלך מכרטיס ברוכים הבאים. תפריט המגש כולל גם השהיה/חידוש, תיקיית ההורדות שלך, ויציאה.
  3. לחיצה כפולה על קובץ .nzb מכניסה אותו לתור. Windows Defender עשוי לבקש פעם אחת לאפשר האזנה לרשת מקומית - אפשר זאת.

מעדיף עותק נייד? ה--windows-x64.zip עדיין עובד: חלץ בכל מקום ולחץ פעמיים על nzbfast.exe (או Start nzbfast.bat) עבור אשף הטרמינל.

מטרמינל (כל פלטפורמה)

nzbfast setup            # interactive server setup (writes config.local.json)
nzbfast serve --open     # start the daemon and open the dashboard
טיפכבר הרצת SABnzbd או NZBGet? דלג על הקלדת אישורים: Settings → Usenet servers → Import from SABnzbd / NZBGet… מוצא את ההתקנה הקיימת שלך ומעתיק את השרתים שלה. יש גם nzbfast import-sab בשורת הפקודה.

מפתח ה-API שלך

בהתקנה חדשה באמת, nzbfast יוצר לעצמו מפתח API בפעם הראשונה שהדימון עולה, ומדפיס אותו פעם אחת בכרזה ממש מתחת לכתובת לוח המחוונים. מכאן והלאה כל בקשה זקוקה למפתח הזה, כך שלוח המחוונים וה-API אינם פתוחים לכל דבר שמסוגל להגיע למכונה.

מה שאתה עושה איתו תלוי באיך הפעלת את nzbfast:

  • אפליקציית macOS, מגש Windows, או serve --open: כלום. הם מעבירים את המפתח לחלון הדפדפן שהם פותחים, לוח המחוונים זוכר אותו, ואתה כבר מחובר.
  • דפדפן שפתחת בעצמך, או לוח המחוונים בטלפון או במחשב אחר: הדף מבקש את המפתח פעם אחת וזוכר אותו מכאן והלאה.
  • Sonarr, Radarr, nzb360 וחברים: הדבק אותו כמפתח ה-SABnzbd או ה-NZBGet שלהם (§11, §12).

המפתח נשמר בקובץ בשם apikey ליד קובץ התצורה שלך, כך שהוא נשאר זהה בין הפעלות מחדש ואפשר לקרוא אותו בחזרה מתי שצריך. ב-macOS וב-Linux הקובץ קריא רק לחשבון שמריץ את nzbfast. הוא נמצא גם בפלט של הדימון עצמו, כך שכרטיס היומן בלוח המחוונים מחזיק אותו אם הטרמינל כבר נגלל.

שדרוג לא משנה דבר.התקנה שכבר קיימת נשארת בדיוק כפי שהייתה, עם מפתח או בלעדיו. מפתח נוצר אך ורק בהרצה ראשונה - כזו בלי הגדרות לוח מחוונים ובלי תור שמור - כי מפתח שמופיע תחת התקנה עובדת היה נועל בחוץ כל Sonarr, Radarr ואפליקציית טלפון שכבר חיברת, בהפעלה מחדש שמעולם לא קישרת לשינוי הגדרות.

כדי להשתמש במפתח משלך במקום, הקלד אותו ב-Settings → Security; הוא חל מיד. הפאנל הזה מחליף את המפתח אך לעולם אינו מציג את הנוכחי, אז קרא את קובץ apikey אם אתה צריך את הערך שנוצר בחזרה. כדי להריץ בלי מפתח כלל, כי משהו שנמצא לפני nzbfast כבר מטפל בהתחברות, הפעל אותו עם NZBFAST_OPEN=1 בסביבה. nzbfast אז נשאר פתוח ואומר זאת במפורש בהפעלה.

אילו מכונות יכולות בכלל להגיע לדימון היא בחירה נפרדת: serve --bind. ברירת המחדל היא 0.0.0.0, כלומר כל ממשק רשת, כי קופסת NAS, טלפון, ו-Sonarr במחשב אחר צריכים כולם להיות מסוגלים להתחבר. --bind 127.0.0.1 מצמצם זאת למכונה שעליה nzbfast רץ, וזה מה שאתה רוצה בשולחן עבודה יחיד שבו שום דבר אחר לא צריך גישה.

3 · איך nzbfast עובד

אוצר מילים מהיר כדי ששאר המדריך ייקרא בקלות:

מונחמשמעות
ספק / שרתשירות Usenet שיש לך חשבון אצלו (Newshosting, Eweka, XS News…). כל אחד מתיר מספר מסוים של חיבורים בו-זמניים.
עמוד שדרההתשתית שמאחורי ספק. מותגים רבים לעתים קרובות מוכרים מחדש את אותו עמוד שדרה - כדאי לדעת, כי שני ספקים על עמוד שדרה אחד מחמיצים את אותם מאמרים. ראה גיוון שרתים.
NZBקובץ XML קטן המפרט את המאמרים שמרכיבים פוסט. זה מה שאתה מזין ל-nzbfast.
PAR2נתוני שחזור המפורסמים לצד רליס. nzbfast מאמת מולם תוך כדי ההורדה ומתקן אוטומטית כשמאמרים פגומים או חסרים.
RAR במצב אחסוןרוב הרליסים ארוזים בכרכי RAR ללא דחיסה. nzbfast מזהה זאת וכותב את הקובץ הפנימי ישירות ל מיקומו הסופי תוך כדי הורדה - בלי שלב פריקה אחר כך.

הצינור מריץ הורדה → פענוח → אימות → חילוץ בו-זמנית. כרטיס הצינור בלוח המחוונים מציג את כל שלושת המסלולים נעים בבת אחת. כשהבייט האחרון מגיע, האימות כבר הסתיים והקובץ כבר מחולץ; זמן "עיבוד לאחר הורדה" של משימה טיפוסית הוא אפס. אם נדרש תיקון, רק אז כרכים ממומשים לדיסק, מתוקנים במקום על ידי מנוע ה-GF(2¹⁶) המקורי (נתונים מעורפלים ששמם שונה או הוזזו בבייטים נמצאים ומאומצים על ידי סריקת בלוקים מחליקה), ומחולצים מחדש - הכול אוטומטי.

הורדות שהופרעו (קריסה, אובדן חשמל, kill -9) מתחדשות מ יומן המאמרים: בייטים שכבר על הדיסק לעולם לא מורדים פעמיים. היומן מתעד היכן נחתו הבייטים של כל מאמר פיזית - אפילו בייטים ש חולצו ישירות אל הקובץ הסופי - כך שחידוש בונה מחדש מהדיסק המקומי ו מאמת מחדש כל מה ששיחזר מול מפת בלוקי ה-PAR2 לפני שהוא סומך עליו.

איך זה משתווה

נמדד מול SABnzbd 5.0.4 ו-NZBGet 26.2 על אותה מכונה, אותם ספקים ואותם קובצי NZB, מתוזמן לקובץ שמיש - הורדה, אימות, תיקון וחילוץ כלולים כולם, כי אז המשימה באמת מסתיימת:

הפער הוא העיבוד לאחר הורדה שהאחרים עדיין צריכים לבצע לאחר שהבייט האחרון נוחת. שני המתחרים כווננו לצורך ההשוואה, לא הושארו בברירות מחדל - SABnzbd בפרט מגיע עם צנרת בקשות כבויה, מה שעולה לו ביוקר, אז היא הופעלה.

שני הבדלים חשובים באותה מידה כמו הזמנים:

  • שטח דיסק. מעבר יחיד צריך פי 1 מגודל הרליס; קליינטים שכותבים כרכי ארכיון ואז פורקים אותם צריכים פי 2. על מכונת בדיקה עם 97 GB פנויים, משימת 87 GB הסתיימה כאן ב-3 m 08 s והשניים האחרים לא יכלו לרוץ בכלל.
  • זיכרון. במשימת ה-190 GB, שיא השימוש היה 3.9 GB מול 9.3 GB של SABnzbd - ו-nzbfast יבצע את אותה משימה בכ-1 GB אם יורו לו (ראה תקציב זיכרון).
חידוש לאחר קריסה, נמדדהרוג הורדה באמצע התעופה (kill -9 ב-15 GB של משימת 34.5 GB) והחידוש מוריד מחדש ~0.3 GB - רק את המאמרים שהיו באמת בתעופה בזמן ההריגה - מול 0.2 GB של NZBGet באותה בדיקה. זה היה פעם הפסד שפרסמנו (15.3 GB הורדו מחדש, כשהיומן לא יכל להסביר בייטים שחולצו ישירות); יומן המיקום תיקן זאת: החידוש משחזר את הבייטים האלה מקובצי הפלט המקומיים ומאמת מחדש כל בייט משוחזר מול מפת בלוקי ה-PAR2 לפני שהוא סומך עליו. כל תרחיש שאנחנו מפסידים מתפרסם לצד הניצחונות, עם השיטה המלאה והמספרים הגולמיים.

4 · לוח המחוונים

פתח את http://localhost:6789 (או את הכתובת של המכונה שלך ממכשיר אחר - פריסת הטלפון מסתגלת אוטומטית). הכול מתעדכן חי, פעם בשנייה. הכרטיסים, מלמעלה למטה:

סרגל כותרת

  • תפריט מגבלת מהירות - תקרות קבועות, אוטומטי · מפנה מקום ל-LAN (מצב מווסת-RTT שנסוג כשמישהו אחר בבית צריך את הקו), או ללא הגבלה.
  • השהה למשך… - השהה הכול למשך 15 דק'/30 דק'/1 שעה/3 שעות עם חידוש אוטומטי, או השתמש בכפתור ההשהיה להשהיה פתוחה. השהיה מיידית: ההעברה הפעילה נעצרת תוך שניות ומתחדשת מאוחר יותר מ היומן, בלי לאבד דבר. (משימות בעדיפות כפייה ממשיכות לרדת, בסגנון SABnzbd.)
  • באנר עדכון מופיע כאן כשגרסה חדשה זמינה (ראה עדכונים).

תפוקה

MB/s חי עם גרף מתגלגל; סימני המים המקווקווים מסמנים את השיא/שפל של הסשן הזה, הקו הדהוי הוא ממוצע נע. מתחתיו, היסטוגרמה מציגה איך דגימות המהירות של הסשן מתפלגות - טיפוסי מול שיא. הרחב את החלון והגרפים מציגים יותר היסטוריה (עד שעה).

אריחי סטטיסטיקה

הורד בסשן זה, עומק התור, ספירות הושלמו/נכשלו, מהירות שיא הסשן.

משאבים - מכונה אחת, ארבע תקרות

מעבד, RAM (מול תקציב הזיכרון של nzbfast), קצב כתיבה לדיסק ורשת על גרף מנורמל אחד, עם ערכים אמיתיים במקרא ואזהרת מקום-נמוך. שום קליינט NZB אחר לא מראה לך זאת; הוא קיים כדי להוכיח נקודה - nzbfast ימצה את הקו שלך, לא את המכונה שלך.

צינור - שלבים חופפים

שלושה מסלולים: הורדה, אימות (בלוקי PAR2 נבדקים), חילוץ. במשימה בריאה כל השלושה נעים יחד.

ספקים

קצב חי לכל שרת, ניצול חיבורים, נתח מהתעבורה, GB לסשן, ו ניקוד השלמת מאמרים לכל החיים (צבוע כששרת יורד מתחת ל-98%). גרף שטח מוערם מציג את תרומת כל ספק לאורך זמן. שורות מתמיינות לפי ביצועים חיים כל 10 שנ' (ניתן להגדרה ב-Settings → Interface) כך שהספק המהיר ביותר שלך תמיד למעלה.

תור

  • גרור שורות לשינוי סדר (בתוך רצועת עדיפות - כפייה/גבוהה עדיין רצים ראשונים); שנה עדיפות בשורה.
  • לחץ על שורה למגירת הפרטים: פסי התקדמות לכל קובץ, ספירות בלוקי אימות, ואיזה שרת תרם כמה למשימה זו.
  • תגים מציגים מצבים מיוחדים: נדחה (איטי), טעינה מקדימה, מושהה (ראה כלי ביצועים).
  • גרף ספירה לאחור עוקב אחר סך ה-GB שנותרו לאורך התור.

עיון באינדקס

חפש בכל מה שהאינדקסר המובנה קטלג מהקבוצות במעקב שלך (ראה אוטומציה) והורד בלחיצה אחת - בלי אינדקסר חיצוני. שורת הסטטוס מציגה את התקדמות הסריקה; סרוק עכשיו מכריח מעבר.

רשימת מעקב

היסטוריה

הורדות אחרונות, שורה לכל אחת. משימות שנכשלו מציעות נסה שוב (מתחדש מהיומן). ארכיונים מוצפנים מציגים בקרת שחרור 🔑 - הזן את הסיסמה והמשימה מסתיימת במקום. רצועת תקינות-האימות מגרפת בלוקי PAR2 פגומים לכל הורדה - זנב עולה פירושו שמאמרים מגיעים פגומים.

הכרטיס מציג עשר הורדות כברירת מחדל, והשאר במרחק לחיצה אחת, בכפתור ▤. הסטטוס, המיקום והסיבה לכישלון של משימה נמצאים מאחורי לחיצה על השורה עצמה, כך שהמקרה הרגיל - מה הסתיים, באיזה גודל, מתי - נשאר קריא בלי גלילה. לחלופין, גרור את הקצה התחתון של הכרטיס כדי שהרשימה תיגלל בגובה שתבחר. History rows ב-Settings → Interface משנה את העשר האלה; מכיוון שזו תכונה של הדימון ולא של הדפדפן שלך, היא חלה על כל מכשיר שמסתכל על ההתקנה הזו. Colour History names, לצידו, צובע שמות שהושלמו בירוק ושנכשלו באדום; בכיבוי השמות נשארים נייטרליים, והנקודה הצבעונית ופרטי השורה עדיין אומרים מה זה מה.

קישורי nzblnk

לוחות מסוימים, בעיקר גרמניים והולנדיים, מפרסמים קישור nzblnk: במקום קובץ NZB. הפוסט מעורפל, ולכן אין שם קובץ כלשהו שאפשר לקשר אליו. במקום זאת הקישור נושא כותרת, h=, שהיא מפתח חיפוש ולא מיקום, ולצדה כותרת t=, סיסמה p= וקבוצה g= אופציונליות. מישהו צריך קודם ללכת ולמצוא את הפוסט.

nzbfast מחפש את הכותרת קודם באינדקס שלו עצמו, מה שאינו דורש רשת כלל, ורק אם זה מחטיא הוא פונה לאינדקסרי החיפוש שהגדרת (Settings → Search indexers, §9), תחת אותם תקציבים יומיים ואותה נסיגה כמו כל חיפוש אחר. הכותרת הופכת לשם המשימה והסיסמה מוחלת על המשימה אוטומטית.

  • הדבקה או גרירה עובדת בכל התקנה, כולל Docker וקופסאות NAS: העתק את הקישור מהלוח והדבק אותו בכל מקום בלוח הבקרה.
  • לחיצה על קישור דורשת שהסכימה תהיה רשומה אצל שולחן העבודה שלך. היישום מתוך ה-DMG של macOS רושם אותה, ומתקין Windows מציע אותה כמשימה: הוא שואל קודם, ומשאיר את הסכימה בשקט אם NZB Monkey או NZBDonkey כבר מחזיקים בה. ל-tarball הפשוט של macOS, ל-Homebrew ולהתקנות Linux אין מטפל שולחן עבודה, ושם ההדבקה היא הדרך פנימה.
  • הפענוח מוגבל בקצב בכוונה. רישום סכימה מציב אותה במרחק שאלת דפדפן אחת מכל עמוד שאתה מבקר בו, ולכן הקישורים מוגבלים לדקה ורק הראשונים שבכל דקה רשאים להגיע לאינדקסרים שלך; מעבר לכך התשובה מגיעה מהאינדקס המקומי בלבד.

6 · קיר הפוסטרים

לחץ 🎬 קיר בכותרת. הקיר הופך את האינדקס שלך לדפדפן מדיה: כל סרט ורליס טלוויזיה שזוהה כאריח פוסטר עם דירוג, שנה, ז'אנרים, שחקנים ותקציר - קבוצות הדיון שלך, ניתנות לעיון כקטלוג.

  • לשוניות לסרטים / סדרות / אחר, חיפוש מיידי ושבעה סדרי מיון: בשבילך, הפוסטים החדשים ביותר, שנת יציאה, המדורגים ביותר, כותר א–ת, הגדולים ביותר ועם הכי הרבה פוסטים.
  • מותאמים בלבד פעיל כברירת מחדל, ומסתיר זבל לא-מזוהה; צ'יפ "+N לא מותאמים" חושף אותו.
  • לחץ על אריח לגיליון הפרטים: תקציר, דירוג IMDb והצבעות, שחקנים - ו-▶ נגן (צפה בו מיד בתצוגה מקדימה, ראה §7) או ⬇ הורד.
  • ✎ תקן התאמה - אם כותר הותאם לסדרה או סרט שגויים, בחר את הנכון מפוסטרים מועמדים, או הזן כותר/שנה/סוג ידנית. טקסט ידני לעולם לא נדרס על ידי המעשיר. ↻ רענן מטא-נתונים מוריד מחדש כותר אחד; Settings → Indexing יכול לרענן הכול או למחוק/לבנות מחדש את כל האינדקס.
  • מטא-נתונים הם ללא מפתח כברירת מחדל - TVmaze, iTunes, מאגרי IMDb, Wikidata, Wikipedia ו-AniList לא צריכים חשבונות. מפתח OMDb (חינמי, הרשמה במייל בלבד - יש עוזר הרשמה ב-Settings → Indexing) משפר התאמת סרטים; מפתח TMDB מכובד אם כבר יש לך אחד.
  • בשבילך מדרג את הקיר לפי פרופיל טעם שנבנה במכונה הזאת מתוך ההיסטוריה שהשלמת ומרשימת המעקב שלך: ז'אנרים מועדפים, האם אתה נוטה לסרטים או לסדרות, ובערך איזו תקופה. כותרים שכבר יש לך שוקעים לתחתית במקום להיעלם, וכיתוב „כי אתה צופה ב…” מציין על מה הסתמך. בלי היסטוריה המיון נופל חזרה לעם הכי הרבה פוסטים, כך שהלשונית לעולם אינה ריקה. שום דבר מזה אינו יוצא מהדימון.
  • לא מעניין על כרטיס מסתיר את הכותר הזה, והסתרה של כמה כותרים דומים מלמדת את הקיר: הוא מציע מסנן שאפשר לאשר בלחיצה אחת („להסתיר מעכשיו את כל כותרי הריאליטי?”). כל מה שהסתרת, וכל מסנן שנלמד, מופיע תחת מוסתרים ומסננים וניתן לבטלו שם.
  • נקודת זמינות קטנה על כרטיס היא פסק הדין של האורקל (§13): „?” בכתום פירושו לא ודאי אצל הספקים שלך, אדום פירושו שהחלקים שלו חוזרים וחסרים. קבוצות שלמות שמפונות כרגע נושאות תג מפונה.

7 · תצוגה מקדימה ואימות

אתה לא חייב להמתין לסיום ההורדה כדי לדעת שזה הקובץ הנכון. פתח אותו תוך כדי ההורדה, בדוק שהתוכן, השפה והאיכות הם מה שציפית, ובטל מוקדם אם לא - במקום לגלות זאת רק אחרי ההורדה המלאה.

  • ▶ נגן על הקיר (או /m3u/<id>) מוסר לנגן המדיה שלך כתובת URL; הדימון מתחיל או מנצל מחדש את ההורדה שמאחוריה.
  • נקודת הקצה /stream/<nzo_id> מגישה את הקובץ עם תמיכת טווח HTTP מלאה תוך כדי הורדתו. בדיקת כל נקודה עובדת: דגום את דקה 40 ו המאמרים לאזור הזה מקודמים לראש תור ההורדה - הוא נפתח שם בדרך כלל תוך כמה שניות במקום דקות. הראש וה זנב של הקובץ מורדים תחילה כך שנגנים מוצאים את נתוני האינדקס שלהם מיד.
  • מצב ספרייה: קטגוריות המפורטות ב-library_cats הופכות לרשומות מטא-נתונים בלבד מיידיות - קובץ .strm מופיע מיד, הזמינות מאומתת ברקע, וההורדה האמיתית מתחילה כשאתה פותח אותו לראשונה.
הערת נגןVLC, IINA, mpv ו-Infuse כולם פותחים כתובות /stream. לבדיקה ממכונה אחרת השתמש בכתובת ה-LAN של המכונה שלך במקום localhost.
הערת אימותעם מפתח API מוגדר, פתיחת רשומת ספרייה חונה דרך /stream/<id> דורשת אסימון לכל משימה (?t=…) - נגנים לא יכולים לשלוח מפתחות API, כך שמסירת ה-/m3u ומצביע ה-.strm משבצים אותו עבורך; יצירתו (/m3u) דורשת את המפתח. הגשת בייטים פשוטה של הורדה שכבר פעילה נשארת פתוחה, ו התקנות ללא מפתח מתנהגות כמו קודם.

כיצד נשמרות סיסמאות הספקים שלך

סיסמאות הספקים בקובץ config.local.json הן מעורפלות, לא מוצפנות. הן נשמרות בצורת obf1: ואחריה צורה מקודדת, כך שהקובץ אינו נקרא כטקסט גלוי אם הוא מופיע בצילום מסך, בהודעה בפורום, בדוח תקלה או על מסך שמישהו אחר יכול לראות.

נהיה ברורים לגבי מה זה נותן ומה לא:

  • זו אינה הצפנה והיא אינה מגנה כלל מפני מי שיש לו הקובץ. השיטה נמצאת בקוד הפתוח שלנו והמפענח מגיע בתוך nzbfast, כך שכל מי שמחזיק בקובץ משחזר את הסיסמה תוך שניות. התייחס לקובץ כאל סוד בדיוק כפי שהיית עושה אילו הסיסמאות היו קריאות.
  • זה מסיר את הדליפה המקרית, שהיא הנפוצה. קובצי הגדרות מודבקים לשרשורי תמיכה ונתפסים בצילומי מסך הרבה יותר מאשר נגנבים מהדיסק.
  • סיסמה שהקלדת בעצמך כטקסט גלוי ממשיכה לעבוד. nzbfast קורא את שתי הצורות, כך שהגדרות שנערכו ביד וייבוא מלקוחות אחרים לעולם אינם נשברים; בשמירה הבאה הוא כותב את הצורה המעורפלת.
  • הקובץ גם נכתב כך שרק החשבון שמריץ את nzbfast יכול לקרוא אותו (מצב 0600 ב-macOS וב-Linux).

לשם השוואה, NZBGet ו-SABnzbd שומרים שניהם את סיסמאות הספקים כטקסט קריא בקובצי ההגדרות שלהם. אנחנו רואים בערפול שיפור קטן על כך, לא תכונת אבטחה.

למה לא מחזיק המפתחות של המערכת? Keychain של macOS, מנהל האישורים של Windows ושירותי הסודות של Linux היו נותנים הגנה אמיתית, ואולי נחזור לזה. שני דברים עוצרים אותנו היום. הגישה למחזיק המפתחות קשורה לזהות היישום, ו-nzbfast עדיין אינו חתום, ולכן ההתראות וההתנהגות אחרי כל עדכון גרועות. וחלק גדול מההתקנות הוא Docker, שרתים בלי מסך וקופסאות NAS שבהן אין מחזיק מפתחות כלל, מה שהיה מותיר שני מסלולי אחסון שונים לשמור נכונים. פורמט אחד מובן היטב שמתנהג אותו דבר בכל מקום הוא, בינתיים, העסקה הטובה יותר.

לשתי אפשרויות נוספות לכל שרת עדיין אין פקד בלוח הבקרה: הוסף אותן ידנית ברשומה של אותו שרת בקובץ config.local.json (ראה §17) והפעל מחדש.

דיסק ומכסה חי

ספרייה, אבטחה, ממשק

ספרייה: קטגוריות המטופלות כרשומות ספרייה מיידיות + מרווח בדיקה חוזרת. אבטחה: מפתח ה-API המלא (הכול) ומפתח ה-NZB (הוספה בלבד - בטוח לתת לאתרי אינדקסרים), שניהם ניתנים להחלפה חי. כל תיבה מחליפה את המפתח שהיא שייכת לו ברגע שאתה יוצא מהשדה, והשארת תיבה ריקה שומרת על המפתח שכבר יש לה. למפתח ה-API יש גם Show, שחושף ומעתיק את המפתח הנוכחי כדי שתדביק אותו ב-Sonarr, ב-Radarr או ב-NZB360 מתי שיתאים לך, ו-Create new, שמנפיק מפתח חלופי - הישן מפסיק לעבוד מיד, ולכן כל מה שכבר מחובר צריך לקבל את החדש. שניהם מותנים במפתח ה-API עצמו: מפתח ה-NZB להוספה בלבד אינו יכול לקרוא אותו, וזו כל הנקודה במפתח הזה. מהיכן מגיע המפתח בהתקנה חדשה, ראה §2. ממשק: צלילי לחיצה, התראות שולחן עבודה בהשלמה, מרווח מיון מחדש של ספקים.

יחידות מהירות live קובע כיצד מוצגת כל מהירות בלוח הבקרה: מגה-בייט (MB/s, המקובל במנהלי הורדות, ברירת המחדל) או מגה-ביט (Mb/s, כפי שספקיות מציינות קווים). גדלי קבצים נשארים בבתים בכל מקרה. זו תכונה של הדימון ולא של הדפדפן שלך, ולכן היא חלה על כל מכשיר שמביט בהתקנה הזאת.

מתקדם: הגדרות בלי פקד בלוח הבקרה

לארבע הגדרות אין פקד בממשק ואין דגל בשורת הפקודה. קבע אותן דרך ה-API (§16), למשל /api?mode=config&name=verify_mode&value=lean&apikey=…. כמו כל היתר הן נשמרות אל settings.json.

שםמה היא עושה
verify_modefull | fast | lean (ברירת מחדל fast). lean הוא הדחיפה למעבדים איטיים: כמו fast, אך מדלג גם על ה-CRC של yEnc לכל מאמר ברגע ש-PAR2 מכסה קובץ, ומשאיר שכבת CRC32 אחת במקום שתיים. הורדות ללא PAR2 שומרות על ה-CRC של המאמרים, והאימות והתיקון בסוף המשימה אינם משתנים בשני המקרים. אימות מהיר שלמעלה הוא אותו פקד עצמו עבור full מול fast.

רשימת מעקב

האוטומציה הפשוטה ביותר: הוסף כותר בלוח המחוונים, קבע העדפות איכות, סיימת. רליסים חדשים נתפסים כשהם מופיעים בקבוצות המאונדקסות שלך; עותקים באיכות טובה יותר משדרגים תפיסות קודמות; תצוגת לוח שנה מציגה מה עומד להגיע.

11 · Sonarr, Radarr וחברים

nzbfast דובר את ה-API של SABnzbd באופן מקורי, כך שכל *arr עובד מהקופסה - והוא יכול לשמש גם כאינדקסר שלהם.

כקליינט ההורדות

  1. ב-Sonarr/Radarr: Settings → Download Clients → הוסף SABnzbd.
  2. מארח: מכונת ה-nzbfast שלך · פורט: 6789 · מפתח API: מפתח ה-API המלא שלך (היכן למצוא אותו: §2).
  3. קטגוריה כרצונך (לדוגמה tv / movies). בדיקה → סימון ירוק → שמור.

תור, היסטוריה, סטטוס לכל משימה, "הסר ומחק", ניסיון חוזר וניתוב קטגוריות כולם מתנהגים כפי שה-*arrs מצפים.

כאינדקסר (newznab)

  1. Settings → Indexers → הוסף Newznab.
  2. כתובת: http://<host>:6789/ · נתיב API: /api · מפתח: מפתח ה-API שלך.
  3. nzbfast מגיש שאילתות caps, search, tvsearch ו movie מהאינדקס שלו עצמו של הקבוצות במעקב שלך, ו /getnzb/<id> מחזיר את ה-NZB.
הדלק קודם את האינדקסר המובנה (Settings → Indexing). הוא כבוי כברירת מחדל, וכל עוד הוא כבוי החזית הזו עונה לכל שאילתה ב-<error code="101"> במקום בתוצאה ריקה, כך שטעות מתגלה כשאתה מוסיף את האינדקסר ולא שבועות אחר כך.

למה בכלל? אינדקסר באירוח עצמי של בדיוק הקבוצות שמעניינות אותך: בלי חשבונות, בלי מגבלות קריאות API, שימור עמוק ככל שתיתן לו לסרוק. זו תוספת לאינדקסרים הרגילים שלך ולא תחליף, מפני שהוא מוצא רק את מה שפורסם תחת שם קובץ אמיתי.

13 · כלי ביצועים

בדיקת ביצועי מערכת

לחיצה אחת מודדת את שלוש התקרות שלך - תפוקת רשת (בדיקה אמיתית של 8 שניות מרובת-חיבורים), קצב אימות מעבד, ומהירות כתיבה לדיסק - ופותחת בתשובה: מהירות ההורדה המרבית הצפויה שלך ואיזו תקרה היא המגבלה. הפס הקצר ביותר הוא צוואר הבקבוק שלך; האחרים מציגים את המרווח שלהם. תזמן אותה (כל 6 שעות → שבועי) וכל הרצה נרשמת לטבלת היסטוריה, כך ש אתה יכול לראות מתי הספק, ה-ISP או החומרה שלך שינו התנהגות. הרצות מתוזמנות קורות רק כשהתור פנוי.

כוונון חיבורים

מודד ספק אחד במספרי חיבורים עולים וממליץ על ההגדרה - יותר שקעים עוזרים עד שהספק או הקו שלך רוויים, וחלק מהספקים מענישים על בקשת יתר. בדוק הכול משווה כל ספק, ואז מפרץ את כולם יחד כדי לבדוק שהמאגר מרווה את הקו שלך.

גיוון שרתים

דוגם STAT מאמרים לאורך גילאים בכל שרת ומקבץ ספקים לפי פערים משותפים: ספקים עם ~100% מאמרים חסרים משותפים הם אותו עמוד שדרה (כפולים לשחזור); עצמאיים באמת מרחיבים את הכיסוי שלך. מסתיים בהמלצה בשפה פשוטה.

אינטליגנציית תור אוטומטית

  • דחייה אוטומטית: הורדה שצולעת על שרת איטי בודד בזמן שמשימות אחרות ממתינות מוחנה בסוף (היומן שומר את התקדמותה) ומנוסה שוב כשהתור פנוי.
  • טעינה מקדימה בשרתים פנויים: שרתים שלא יכולים לעזור למשימה הפעילה (ה עותקים שלהם נעלמו) מתחילים להוריד את המשימה הבאה בתור בינתיים. שום קליינט אחר לא מבצע חפיפה בין-משימתית.
  • ספיגה בין-משימתית: בזמן שהזנב של משימה שהסתיימה (אימות/חילוץ) מסתיים על הדיסק, ההורדה של המשימה הבאה כבר מחזיקה בקו.

אורקל הזמינות

הסרות הן הסיבה העיקרית לכישלון הורדה ביוזנט, והן ניתנות לחיזוי: אותו רליס נעלם בעמוד שדרה אחד בעוד שאחר עדיין מחזיק אותו. nzbfast מנהל פנקס קטן של מה שהספקים שלך באמת סיפקו, ומוציא תקציב זעיר של בדיקות STAT בזמן המתנה (כמה מאות בשעה לכל שרת, לעולם לא במהלך הורדה) כדי לשמור אותו עדכני. הוא לעולם אינו מוריד מטען לשם כך.

מה יוצא לך מזה:

  • פסק זמינות על כרטיסי הקיר ועל שורות האינדקס (§6): „?” בכתום ללא ודאי אצל הספקים שלך, אדום לאבוד בוודאות. היעדר סימון פירושו שהכול נראה תקין.
  • תג מפונה על קבוצות שבהן פוסטים טריים כבר מוסרים, כדי להבחין בין קבוצה גוססת לבין רליס ביש מזל.
  • דלג על ספקים שלפי האורקל כבר אין להם (הגדרות, כבוי כברירת מחדל, ניסיוני): כשהבדיקה בטוחה שעמוד השדרה של ספק מסוים איבד רליס, הוא מדולג מיד עבור ההורדה הזאת במקום להמתין לכישלונו. את הספק האחרון שנותר לך הוא לעולם לא ידלג.

פסק הדין הוא חיזוי מתוך ראיות, לא ערובה. לתשובה חד-משמעית על NZB בודד, nzbfast check (§15) סופר את המאמרים בפועל.

תקציב זיכרון - ומה עולה זיכרון נמוך

כל מטמוני המנוע חולקים תקציב אחד (ברירת מחדל ¼ מה-RAM הפיזי, מהודק ל- 256 MB–16 GB). קבע אותו במפורש עם מגבלת זיכרון ב-Settings, או --mem-limit בשורת הפקודה.

nzbfast בנוי לספוג את הרשת שלך ואת הדיסק שלך בו-זמנית, וה-RAM הוא מה שמאפשר לו לעשות את שניהם במעבר יחיד: מאמרים מפוענחים, מאומתים ונכתבים ישר להיסטים הסופיים שלהם, כך שכרכי ארכיון לעולם לא צריכים לגעת בדיסק בכלל. הרעב אותו מזיכרון ושום דבר לא נשבר - לכל מטמון יש נתיב גלישה, והמנוע מתדרדר ליותר קלט/פלט דיסק במקום swap או כשל. אבל הגלישה הזו אינה חינם, ובמשימות גדולות אתה יכול למדוד אותה.

נמדד על מכונה אחת וקו אחד (M1 Ultra, 10 GbE), אותם קבצים בכל תקציב. כל הרצה הפיקה תוצאה נכונה, מאומתת במלואה, מחולצת:

  • עד ~35 GB, זיכרון נמוך הוא חינם. קבוצת העבודה נכנסת בלי קשר, כך ש מכונת 4 GB מסיימת משימה כזו מהר כמו מכונת 64 GB.
  • מעבר ל-~87 GB אתה משלם 20–40% - אבל רק כשהקו שלך מקדים את הדיסק שלך. בלוקי אימות וכרכי ארכיון שהיו נשארים ב-RAM נכתבים החוצה ונקראים בחזרה במקום, וזה עולה זמן רק אם הרשת יכולה לספק מהר יותר משהדיסק יכול לספוג את התעבורה הנוספת. ה-20–40% שלמעלה נמדד על 10 GbE; אותה משימת 87 GB באותם תקציבים על קו ~2.4 Gbps לא הראתה עונש בכלל (‎−1 עד ‎+7%, בתוך רעש הרצה-להרצה). העונש הוא פונקציה של כמה רחוק הקו מקדים את הדיסק, לא של גודל המשימה - בחיבור ביתי טיפוסי תקציב קטן הוא כמעט חינם אפילו במשימות גדולות מאוד.
  • העונש מגיע למישור. ברגע שמשימה גדולה מספיק כדי לגלוש, כל תקציב מוגבל גולש בערך באותה כמות - הרצות ה-2 GB, ה-1 GB וה-256 MB קוראות בחזרה בעיקרון את אותו מספר בלוקים מהדיסק, ומסתיימות בתוך רעש זו מזו. אז מעט יותר RAM מתחת לסף שמונע גלישה לחלוטין לא קונה בחזרה את העלות: תן לו מספיק כדי לשמור את המשימה בזיכרון, או שהמספר המדויק בקושי משנה.
המלצהתן ל-nzbfast בערך 2 GB תקציב לכל 100 GB של המשימה הגדולה ביותר שאתה מוריד, והשאר את ברירת המחדל לבד אחרת - ¼ מה-RAM הוא כבר התשובה הנכונה ברוב המכונות. בפועל: 4 GB RAM מכסה משימות עד ~35 GB במהירות מלאה; 8–16 GB שומר גם משימות של 100 GB-פלוס שם; NAS של 2 GB יסיים כל דבר שתזרוק עליו, אבל התייחס אליו כאל מוריד ברקע ולא כאל משהו שירווה קו מהיר.

על NAS קטן, הורד גם את חיבורים (2–4) יחד עם התקציב. בתקציב 256 MB ו-2 חיבורים, שיא הזיכרון נשאר קרוב ל-190 MB - בנוחות בתוך מה שיש ל-NAS של 2 GB פנוי. שים לב שבנקודה הזו מספר החיבורים, לא הזיכרון, הוא מה שמגביל אותך: אותה משימת 35 GB לקחה 286 s במקום 65 s. זו הצורה הכנה של הפשרה - הוא תמיד יסיים, ויסיים נכון; הוא פשוט לא יספוג את הקו.

בדיקות ביצועים מורצות מחדש לכל מהדורה; השיטה והמספרים לכל מכונה מתפרסמים לצד התוצאות.

14 · עדכונים

  • עדכונים הם הודעה בלבד: nzbfast לעולם אינו מוריד או מחליף את הקובץ הבינארי של עצמו, ואין בו קוד שמסוגל לכך. כשקיימת גרסה חדשה, הכותרת מציגה ⬆ v X זמינה - הורד; הצ'יפ מקשר לעמוד ההורדות הרשמי (הקישור קבוע באפליקציה ולעולם אינו מגיע ממניפסט העדכון). התקן את הגרסה החדשה באותו אופן שבו התקנת את הנוכחית.
  • nzbfast בודק גרסאות חדשות פעמיים ביום. כבה את בדוק עדכונים (הגדרות) והוא לא ייצור קשר עם מניפסט העדכון כלל; כתובת URL ריקה לבדיקת עדכונים עושה את אותו הדבר.

קובץתוכן
config.local.jsonאישורי שרת ואפשרויות לכל שרת. נוצר על ידי האשף; ניתן לעריכה ב-Settings. שמור אותו פרטי. הסיסמאות מעורפלות, לא מוצפנות.

apikeyמפתח ה-API ש-nzbfast יצר לעצמו בהרצה ראשונה (§2). חי ליד התצורה; קריא רק לחשבון שמריץ את nzbfast ב-macOS וב-Linux. אל תמחק אותו כדי לקבל מפתח חדש: בהתקנה שכבר רצה, שום דבר לא מחליף אותו והדימון עולה בחזרה בלי מפתח כלל. קבע מפתח חדש ב-Settings → Security במקום זאת.

<config>/.spool/מצב התור (שורד הפעלות מחדש), קובצי NZB לכל משימה, יומן שימוש, היסטוריית בדיקות ביצועים, מטמון אמנות פוסטרים.
יומן מאמריםבתוך תיקיית הפלט של כל משימה בזמן שהיא לא שלמה - מפעיל חידוש לאחר קריסה וניסיון חוזר. מוסר בהצלחה.
כלים חיצונייםאין צורך בשום דבר - חילוץ RAR ותיקון PAR2 מקוריים. אם סט אקזוטי אי פעם צריך unrar או par2 חיצוני כנפילה לאחור, nzbfast מחפש ליד קובץ ההפעלה שלו, ואז ב-$PATH.

תסמיןבדוק
הורדות איטיותהרץ בדיקת ביצועי מערכת - היא נוקבת בצוואר הבקבוק במפורש. אם זו רשת: הרץ כוונון חיבורים, בדוק מספרי חיבורים לכל שרת, וודא שהספקים שלך אינם כולם עמוד שדרה אחד (גיוון שרתים).
איטי רק במשימות גדולות מאוד
(NAS או מכונת RAM-נמוך)		צפוי, וניתן למדידה: תקציב זיכרון מורעב מגלים מטמונים לדיסק ועולה 20–40% מעבר ל-~87 GB. ראה תקציב זיכרון למספרים וכמה RAM לתת לו. משימות קטנות יותר לא מושפעות.
הורדה נכשלת "מאמרים חסרים"הפוסט פג או הוסר אצל הספקים שלך. ספק שני על עמוד שדרה אחר מציל את רובם. nzbfast check חוזה זאת לפני ההורדה. והקיר מסמן מראש את אלה שקרוב לוודאי נעלמו, באמצעות נקודת הזמינות שלו (§13). כישלון ראשון מסוג זה חוזר על עצמו פעם אחת מאליו אחרי המתנה, משום שהשהיית תפוצה נראית בדיוק אותו הדבר ונפתרת מעצמה.
ארכיון שהסתיים רוצה סיסמהשורת ההיסטוריה מציגה 🔑 - הזן את הסיסמה שם; המשימה מסתיימת במקום.
ארכיון לא נחלץכשלי סיסמה ותיקון מציגים את עצמם בשורת ההיסטוריה. לכל השאר יש פתח מילוט: הגדרות → תיקיית מעקב ועיבוד לאחר הורדה → חילוץ עם unrar חיצוני (הגדרה מתקדמת) מוסר את החילוץ לתוכנת unrar המותקנת במחשב שלך במקום המחלץ המובנה. אחרת השאירו כבוי: הנתיב המובנה מהיר יותר בכל צורה שמדדנו, ופרסומים מוסווים עם שמות hash תמיד משתמשים בו ממילא, כי unrar אינו יכול לעקוב אחר שינויי השמות שלהם. אותו מתג עבור הרצות nzbfast get הוא משתנה הסביבה NZBFAST_NO_NATIVE_UNRAR=1. אם unrar חילץ ארכיון שהמחלץ המובנה סירב לו, אנא דווחו כדי שנתקן את הנתיב המובנה.
Sonarr/Radarr לא מצליחים להתחברפורט 6789 נגיש? מפתח API נכון (מפתח מלא, לא מפתח NZB)? סוג הקליינט מוגדר ל-SABnzbd?
לוח המחוונים מבקש מפתח API שמעולם לא קבעתיהתקנה חדשה יוצרת אחד לעצמה ומדפיסה אותו פעם אחת בהפעלה (§2). הוא נמצא בקובץ apikey ליד התצורה שלך, וגם בפלט ההפעלה. או הקלד מפתח משלך ב-Settings → Security מדפדפן שכבר מחובר.
שום דבר ברשת לא מצליח להגיע לדימוןבדוק את --bind: 127.0.0.1 משרת רק את המכונה שעליה nzbfast רץ. ברירת המחדל, 0.0.0.0, משרתת כל ממשק. אחר כך בדוק את חומת האש של המכונה עצמה עבור פורט 6789.
כרטיס העיון נשאר קטןהאינדקסר גדל ברקע - בדוק שקבוצות Settings → Indexing מוגדרות, ותן ל-העמקה בכל סריקה זמן לצבור היסטוריה. "סרוק עכשיו" מכריח מעבר; שורת הסטטוס מציגה התקדמות חיה.
הקיר מציג אמנות שגויה/חסרהגיליון פרטים → ✎ תקן התאמה או ↻ רענן מטא-נתונים. חיפושי סרטים משתפרים עם מפתח OMDb חינמי.
הדימון לא מתחיל: פורט בשימושמופע אחר רץ - או שנה את --port.
