# Environment variables

Every `NZBFAST_*` variable read by the code in `crates/*/src`, grouped
Supported first. "Supported" means an operator may reasonably set it;
"Debug-only" covers rollout kill-switches, bench/tuning knobs, and test
harness plumbing - they can vanish or change meaning between releases.

Strings like `__NZBFAST_INDEX__`, `__NZBFAST_INDEXERS__`,
`__NZBFAST_SPOTS__`, `__NZBFAST_LOCALE__`, and `__NZBFAST_UI_TOKENS__`
also appear in the source but are HTML placeholder tokens substituted
into the embedded dashboard pages, not environment variables.

## Supported

| Name | Purpose | Default | Class |
|---|---|---|---|
| `NZBFAST_CONFIG` | Config file path, same as `--config`; makes every subcommand and the daemon agree on one file (the container image sets `/config/config.json`). A path, not inline JSON - a value starting with `{` is refused. If the file is absent, a SABnzbd install's server list is used instead when one is found (on the machine, or beside this path), with a warning naming the file it came from; that applies whether the path came from here, from `--config`, or from the default | `config.local.json` in the cwd | Supported |
| `NZBFAST_STORAGE` | Force storage-type detection for the output path: `rotational`, `ssd`, or `auto` | `auto` (detect) | Supported |
| `NZBFAST_READ_TIMEOUT_SECS` | Read-stall timeout for pooled NNTP connections, in seconds. On the non-adaptive path it is the flat whole-response timeout. With adaptive timeouts on (the default), setting this ABOVE 10 also lifts the adaptive pre-first-byte ceiling to the same value (lift-only, never below the 2-10 s window) - the accommodation for providers with slow cold-storage lookups. Set `NZBFAST_ADAPTIVE_TIMEOUT=0` to return to the flat timeout entirely | 30 | Supported |
| `NZBFAST_ADAPTIVE_TIMEOUT` | Per-knob override of the "Adaptive connection timeouts" setting (a two-phase bound: a pre-first-byte budget adapting to each server's measured response latency, so dead connections are detected in 2-10 s, plus an 8 s no-progress deadline once bytes flow; a slow but alive transfer is never cut for exceeding a flat cap): `1` on, anything else off. Unset, the setting decides (default on) | follows setting | Supported |
| `NZBFAST_DESYNC_FENCE` | `0` disables the §129 3g alignment fence: a DATE pipelined behind every BODY sent to a provider whose 430/423 refusals carry no message-id, so a response dropped upstream is caught at the next read instead of silently charging its refusal to the article behind it. It costs one six-byte command and one short answer per article against such providers, and no round trips. The escape hatch is for a provider whose answers cannot be relied on at all - the pool already retires fencing on its own for a provider that never answers DATE | unset (fence on) | Supported |
| `NZBFAST_RECHECK_430` | `0` disables the TODO 315 late re-ask: when a 430/423 from the LAST live backbone would make an article missing, the article is requeued at the MIDPOINT of the remaining queue and that backbone is asked once more before the verdict is emitted. It exists because a refusal that names its own message-id is still not a true one - measured 28 Aug 2026 against a single provider, a cold slice lost 250 of 23,103 segments to refusals every one of which echoed its article's id, and a re-run of that same slice nine minutes later off the same account lost 19. One re-ask per article per server group, so it terminates; a takedown-flavoured refusal and a promoted (playhead) article are both excluded | unset (re-ask on) | Supported |
| `NZBFAST_RECHECK_430_MAX` | Ceiling on how many articles may be holding a `NZBFAST_RECHECK_430` re-ask at once. It bounds the cost on a wholly dead post, where every article would otherwise take the pass, and it bounds how much damage the consumer cannot see yet - a held verdict is damage the speculative par2 prefetch has not been told about, so past this many holds the refusals go terminal on schedule. A concurrency limit, not a whole-run quota: a slot comes back as soon as its article is answered | 4096 | Supported |
| `NZBFAST_RECHECK_430_HOLD_SECS` | How long one `NZBFAST_RECHECK_430` re-ask may keep an article out of a terminal verdict; `0` removes the bound. Without it the hold has none: the re-asked backbone's own refusal bit is cleared while the article waits, so the article is retirable only by that backbone and dispatchable only by it too, and a backbone that has stopped answering - or is merely slow - keeps the article, and the run, alive. Measured 30 Aug 2026 on a live three-provider install: a last backbone managing one refusal every ~17 s held about 600 articles behind it and a download's tail ran 5 h 46 m. Not derived from `server_outage_mins`, which is a promise about waiting for a server to FETCH and not about withholding a verdict | 900 (15 min) | Supported |
| `NZBFAST_CONN_DARK_SECS` | How long a server may hold no connection at all before it stops blocking a terminal verdict for articles it has never refused, and stops holding the fill gate shut over them; `0` removes the bound. The pool used to count a server as able to answer whenever it still had a WORKER, which is not the same as having a connection: a server whose workers are all parked after failing to dial kept its say, so an article it had never refused could never be settled and no other server was allowed to take it either, and it rotated in the queue for as long as that server stayed alive. Measured 30 Aug 2026 on a live three-provider install: 399 articles pinned at 210 seconds behind two servers that held thirty-four workers and no connection between them. Measured from the last SESSION rather than the last dial, so a server reconnecting inside the window never leaves; suspended entirely while no server is serving, because a verdict is not owed to a fleet that is wholly dark. Not derived from `server_outage_mins`, which is a promise about waiting for a server to FETCH and not about withholding a verdict | 120 (2 min) | Supported |
| `NZBFAST_STALL_ABORT_SECS` | Download stall watchdog: abort when decoded bytes AND outstanding articles are both frozen this long | 180 | Supported |
| `NZBFAST_SIDEFETCH_STALL_SECS` | Recovery side-fetch stall watchdog: abandon a repair's par2-volume fetch when BOTH the articles it has resolved and the pool's deferred count are frozen this long. The sibling of `NZBFAST_STALL_ABORT_SECS` for the pool the tail runs, which had no watchdog until 30 Aug 2026 - a provider that stopped granting connections parked one job's repair for eleven hours, with the queue row reading `Repairing` and nothing repairing. Longer than the download's window on purpose: the tail has already left the network phase, so a long silence is cheaper to sit through than a wrong abort. Zero or unparseable means the default, never an instant abort | 300 | Supported |
| `NZBFAST_TAIL_FANOUT` | Per-knob override of the "Race slow articles" setting: `1` arms the endgame tail fan-out only, `2` also arms it from the moment the queue runs dry, anything else disarms it. Unset, the setting decides (default on, early) | follows setting | Supported |
| `NZBFAST_HEDGE` | Per-knob override of the setting's adaptive straggler hedge (dup race staleness bound 3x the trained article time instead of a flat 8 s): `1` on, anything else off. Unset, the setting decides | follows setting | Supported |
| `NZBFAST_RECYCLE_SLOPE` | Per-knob override of the setting's slow-session recycle (a connection under 25% of its server's per-worker rate after 10 s redials): `1` on, anything else off. Unset, the setting decides | follows setting | Supported |
| `NZBFAST_TTFB_HEDGE` | `1` dup-races an in-flight article once its read has sat ~1 s (or 2x the server's measured response latency, whichever is larger) in pre-byte silence, instead of waiting out the full adaptive pre-byte budget - first answer wins, the waiting read is never killed, and the hedge issue-rate cap bounds the spend. Rides the adaptive read path, so it is inert with adaptive timeouts off. TODO 115: the deadair matrix residual (26 s at the old 2 s floor, 30.5 s at today's 4 s one, vs the ~22 s clean floor) is the budget's floor paid per stall | off | Experimental |
| `NZBFAST_SURGE` | Per-knob override of the settings.json `surge_conns` temporary surge dial: how many EXTRA sockets the whole fleet may hold while an article has been on the wire past the same staleness bound the hedge uses AND no connection is idle to race it on. The loan goes through the live connection target, so the fleet cap sees it; it is given back when the stall clears, and in any case within four staleness bounds. `0` off. Measured worth (TODO 313 item 7): the first two sockets recover 23% of the recoverable loss in the dead-air regime, sixteen recover 65%, so the value is clamped at 4 | off (`0`) | Experimental |
| `NZBFAST_RECYCLE_SLOW` | `1` also redials a connection whose articles lose two duplicate races in a row (reactive variant; largely subsumed by the slope recycle) | off | Experimental |
| `NZBFAST_STEER_DEPTH` | `1` arms M7b.2 depth steering: a server whose windowed (~10 s half-life) per-connection rate falls under 1/4 of the best other live server's tops its pipelines up to depth 1 instead of the configured window, restoring above 1/2 (hysteresis). The server keeps every connection fetching unique work - this bounds how many articles sit parked behind each slow session, which is what turns into the job tail at queue-dry. Composes with stream mode (min of the two caps); a lone server, or a fleet with untrained rates, is never clamped | off | Experimental |
| `NZBFAST_TAIL_TAPER` | `1` arms the TODO 208 item 3 endgame depth taper: as the work still to be handed out falls toward one article per connection, connections top their pipelines up shallower, so the fleet reaches queue-dry holding about one article each instead of `window` each. The stretch between queue-dry and the last article is that in-flight set emptying - `connections x window` articles, 1.13-1.62 GB on the bench fleet whatever the job or the line - and roughly a fifth of it is line-idle, because an article parked behind a slow session cannot be handed to a fast connection that has gone idle. Tapering leaves that work in the QUEUE where it can still be rebalanced. Inert until the queue falls under `window x connections`, so a fast link, where deep pipelining is what earns the throughput, is untouched. When armed, the `[pool]` summary line carries `taper armed, min depth N` (or `taper armed, never bit`) so a run can show the knob arrived without inferring it from the tail it is measuring | off | Experimental |
| `NZBFAST_LINE_CAP` | TODO 208 item 1, the fleet cap: the whole fleet's connection budget, split equally across the servers and still under each account's own `connections` (a pinned server keeps its number). Measured on a 99 Mbit line with five providers: fleet 50 beats the configured 360 by 6.6% wall with zero stall-deadline kills, 13x less duplicate spend and 4.7x less RSS - and the floor rounds then found no rung below that where wall starts to rise, at 99 Mbit or at 247, where fleet 25 beat fleet 125 on wall, memory, cpu, duplicate wire, drain and latency alike. The best fleet does not scale with the line up to a gigabit, where fleet 20 finished a second ahead of fleet 360 - so `25` (5 connections on each of five providers) is the FLOOR, and the default is a curve that never goes below it (TODO 277). Above the floor it climbs in rungs of 5 sockets, planning 150 Mbit of line per socket, to a ceiling of `50`: a line has to read above 3.75 Gbit before the fleet grows at all, and reaches the ceiling at 7.5 Gbit. The ceiling is the measured knee and not an account maximum - on an 87 GB job at 10 GbE, wall is flat at 69-71 s for every fleet from 50 to 360 while cpu rises 2.3x across that flat, and the shipped 25 walled 90 s. The ceiling is also a fleet the SLOW-line ladder cleared - at 99 Mbit fleet 50 / 35 / 25 all walled 544-547 s - which is the bound on what a wrong reading can cost, since the anchor falls back to a typed line speed when nothing has been measured. The reading it sizes from is the daemon's persisted link anchor, so a fast install is on the knee from its SECOND job on; a run with no anchor at all (a CLI `get`, a prefetch sidecar, a daemon that has not finished a job) reads 0, and 0 is the floor. Within a run a governor may grow the fleet as the evidence improves, with hysteresis - a bigger reading has to hold three consecutive seconds, the rungs absorb anything smaller, and the fleet never falls - though it can only ever wake slots that were spawned, so today it binds where the spawn ceiling is above the live target. **The unit changed with the rule on 23 Aug 2026** - it used to be connections per Mbit, default `0.5` - so a stale `0.5` no longer parses and reads as OFF. Two halves: the daemon and the CLI both seed each job's fleet at the cap (no link anchor needed, unlike the per-Mbit rule this replaced, so a bench leg that wants a bigger fleet must now turn the cap off), and within a run the pool walks the live targets down to it in one step - that SHED half still stands down without the daemon's persisted `linkpeak` anchor, so a run with no independent estimate of its line is never resized DOWN mid-flight (the governor's raise is not behind that gate: it multiplies where the shed divides, so a reading that is too low can only leave the fleet where the seed put it). The §112 `live_tune` walker walks inside the cap. `0` (or any non-number) disables both halves, which is the bench A/B arm; any other number is a FIXED fleet for the whole run, governor included - a leg that typed a fleet size is asking for that fleet and not for a floor. **Since TODO 312 item 1 the same dial is a SETTING**, `line_cap_fleet` in settings.json, written from Settings -> Connections & performance -> Total connections across all servers: empty = the curve, `0` = off, a number = that fleet, read at every job build so it needs no restart. This variable still WINS over it wherever it is set at all, which is what keeps every bench driver selecting its own arm on a box that happens to have a number saved in its dashboard - `conntune::line_cap_resolve` is the precedence and its test is the pin. The `[pool]` line carries `line cap N (K sheds)` when the in-run half ran, with ` raised from S` appended after the bracket when the governor grew the fleet | rate-aware, 25 to 50 | Supported |
| `NZBFAST_STALL_SHARE_AWARE` | `0` pins the flat 8 s no-progress stall deadline in place of the TODO 208 item 2 share-aware bound, `clamp(2 x mean body / (line peak / sharers), 8 s, 60 s)`, which stops a connection merely starved by a 360-way share being killed as stalled (311 false kills per job at 100 Mbit). | `NZBFAST_STALL_LIVE` | `0` pins the share-aware bound above to its 21 Aug shape for an A/B leg: sampled once at the start of each body read, and the flat 8 s floor until the run's own line peak has trained. On (default, TODO 208 item 2's warm-up fix) the bound is re-read once a second DURING a silence against the best line evidence the pool has - the run's trained peak, else the daemon's persisted link anchor (the figure the `NZBFAST_LINE_CAP` seed was sized from until that cap became a constant, and still the thing that arms its in-run shed; stamped per job from the second job on), else the gauge's own provisional reading a quarter time constant in. Why: the peak trains 7 s after the FIRST delivered body, which a 100 Mbit line under 360 connections lands 10-27 s into the run, so the whole first wave of bodies - read during the fleet's slow-start storm, the most starved moment of the run - was judged by the floor, and evidence the gauge learned while a connection was already quiet could never reach a wait armed before it. With the share-aware bound alone the 250 Mbit legs still logged 27-42 stall-deadline kills each; this is the half it could not reach | on | Supported |
| `NZBFAST_PEAK_ARRIVALS` | `0` pins the line gauge behind the two knobs above (the §202 saturation gate's `line peak`, which the share-aware stall bound divides) to its 21 Aug feed for an A/B leg: one fold per DELIVERED body. Why: a body is credited when it completes, but its bytes crossed the line over the whole transfer before that, and the gauge's age starts at its first fold - so every body in flight at that instant (on a fleet dialled together, every connection's first body) landed in one clump credited to a window that had barely opened.
